# Experience Log — 2026-08-03

## Lessons Learned

### 1. Define an unfamiliar system problem before trying to solve it

When facing a completely unfamiliar system problem, begin by defining the problem precisely instead of jumping directly to a possible fix. First clarify what the observed phenomenon is and what the relevant metric actually means.

A metric definition should include its measurement object, formula or counting rule, unit, data source, sampling window, aggregation method, and threshold. A number without this context cannot reliably guide diagnosis.

### 2. Establish the end-to-end system flow

Build a system-level processing flow for the problem. AI can help propose an initial flow, but the flow should be checked against documentation, source code, traces, logs, and measurements.

For each stage, identify the input, output, producer, consumer, buffer or queue, synchronization point, and scheduling relationship. The same component may be a producer for one buffer and a consumer for another, so its role must be defined relative to the specific object being analyzed.

### 3. Decompose a symptom into the smallest actionable questions

For example, a high `buffer stuffing` metric may indicate that the producer and consumer are not operating at the same effective speed. However, the metric alone does not prove whether the producer is too fast or the consumer is too slow.

The diagnosis should continue with smaller questions:

- Is the producer generating data too quickly?
- Is the consumer processing data too slowly, blocked, scheduled late, or waiting for another resource?
- Is the buffer capacity or threshold configured incorrectly?
- Is backpressure missing or ineffective?
- Is the metric definition or measurement window hiding the real behavior?
- Who exactly is the consumer of this buffer?
- What object does that consumer operate on?

The consumer could be a CPU thread, a runtime component, a DMA engine, a memory subsystem, an operator pipeline, or an NPU. An NPU can be the consumer of an input buffer and the producer of an output buffer, depending on which buffer is being analyzed.

### 4. Continue refining the problem until one experiment can isolate one variable

The goal of decomposition is to reach an actionable unit, not merely to produce a long list of possible causes. For an NPU-related issue, the analysis may need to separate input transfer, synchronization, operator execution, output transfer, queue depth, memory bandwidth, kernel occupancy, host–NPU overlap, and scheduling.

Each hypothesis should lead to a targeted experiment. The experiment record should state its conditions, content, result, and result analysis. This makes it possible to distinguish a producer bottleneck from a consumer bottleneck and to determine whether the appropriate optimization concerns the NPU, the host, memory movement, synchronization, or system scheduling.

## 经验总结

### 1. 在尝试解决陌生系统问题前，先定义问题

遇到一个完全陌生的系统问题时，不要直接跳到可能的修复方案，而应先准确地定义问题。首先要明确观察到的现象是什么，以及相关指标到底代表什么。

指标的定义应包括测量对象、计算公式或统计规则、单位、数据来源、采样窗口、聚合方式和阈值。脱离这些上下文的数字，不能可靠地指导问题定位。

### 2. 建立端到端的系统处理流程

应当为这个问题建立一套系统级处理流程。可以询问 AI，先让 AI 帮助提出一个初始流程，但之后必须结合文档、源代码、trace、日志和实际测量结果进行验证。

对于每一个阶段，都要明确输入、输出、生产者、消费者、buffer 或 queue、同步点以及调度关系。同一个组件对于不同的 buffer 可能分别扮演生产者和消费者，因此必须结合正在分析的具体对象定义它的角色。

### 3. 把一个现象不断拆解为最小的可行动问题

例如，`buffer stuffing` 指标很高，可能说明生产者和消费者的有效处理速度不匹配。但仅凭这个指标，不能证明到底是生产者过快，还是消费者过慢。

还需要继续拆解为更细的问题：

- 生产者是否生成数据过快？
- 消费者是否处理数据过慢、被阻塞、调度延迟，或在等待其他资源？
- buffer 容量或阈值是否配置不合理？
- backpressure 是否缺失或没有生效？
- 指标定义或测量窗口是否掩盖了真实行为？
- 这个 buffer 的消费者到底是谁？
- 这个消费者作用的对象是什么？

消费者可能是 CPU 线程、runtime 组件、DMA 引擎、内存子系统、算子流水线，也可能是 NPU。具体要看分析的是哪个 buffer：对于输入 buffer，NPU 可能是消费者；对于输出 buffer，NPU 又可能是生产者。

### 4. 持续细化问题，直到一个实验能够隔离一个变量

不断拆解的目标不是罗列大量可能原因，而是把问题细化到可以采取行动的粒度。对于 NPU 相关问题，还可以继续区分输入传输、同步、算子执行、输出传输、queue 深度、内存带宽、kernel 占用率、主机与 NPU 的重叠执行以及调度等环节。

每一个假设都应当对应一个有针对性的实验。测试记录必须说明测试条件、测试内容、测试结果和结果分析。这样才能区分究竟是生产者瓶颈还是消费者瓶颈，并判断优化对象到底是 NPU、主机、内存搬运、同步机制还是系统调度。
