# Experience Log — 2026-09-17

## 经验总结

### 1. 区分 Prefill 和 Decode 的工作负载

Prefill 一次处理整段已知 prompt，sequence length 可能变化，矩阵乘通常有较大的并行度。Decode 则按自回归依赖逐 token 生成，每步的新 token 数通常为 1，许多 Linear 因而表现为 GEMV，并容易受内存带宽限制。KV cache 会复用历史 K/V，避免每步重算全部历史表示，但 context length 仍会随生成增长。

### 2. 分清 tensor shape、输入 token 数和 context length

Tensor shape 描述各维度的大小，例如 `[1, 128, 4096]` 可表示 batch、token 数和 hidden dimension。Decode 每步的新输入 token 数通常固定为 1，而 attention/KV 所覆盖的 context length 会从 128、129 继续增长。判断动态性时要指出具体变化的是哪个维度；不能把 context length 的增长等同于每个算子的 shape 都在变化。

### 3. 理解 static graph 是编译与执行计划的基础

Static graph 在运行前固定或约束算子关系、tensor shape、layout 和内存需求，使编译器与 runtime 能提前选择 kernel、切分计算、融合算子、规划内存与 DMA，并安排流水和双缓冲。Static graph 提供生成执行计划的基础，本身不等同于 scheduler。

### 4. 理解 NPU 为何偏好固定 shape

NPU 通常以较少的运行时灵活性，换取更充分的预先规划和更高的执行效率。固定 shape 有利于提前安排数据流、内存和流水线；这不代表 NPU 只能做乘加，也不代表 GPU 只能执行动态 shape。

### 5. 用合适的方法处理 dynamic shape

实际 shape 与静态图不匹配时，可以考虑 padding、bucketing、chunking、复用已有图或重新编译。选择取决于额外计算、图复用和调度开销。若动态部分无法匹配已有的 NPU static graph，也没有合适的固定块可切分，就可以交给 GPU 执行。

### 6. 不要把 NPU 调用时间直接归因于硬件

观察到的调用时间可能包含 scheduling、communication、quantization 和 computation 等成本。OPMASK 通过逐阶段启用 pipeline 并比较阶段差值，隔离这些开销。即使测出 NPU execution path 较慢，也不能仅凭这一结果断定 NPU 硬件本身较慢。

### 7. 分开分析硬件、kernel、framework、backend 和 runtime

实际性能由硬件、kernel、framework、backend、runtime 及 workload 共同影响。同一 NPU 在不同框架或软件栈下可能表现不同。比较 CPU、GPU、NPU 或不同 backend 时，要控制 framework 等变量，避免把软件栈造成的差异都归给硬件。

### 8. 区分异步执行、同步和数据拷贝

RPC 可以同步或异步；异步执行仍要在依赖结果时等待。Synchronization 的作用是确认设备结果已完成且对后续操作可见，它不等同于 memcpy。共享内存可以减少数据拷贝，但 launch、同步、内存可见性和设备协调仍有开销。

### 9. 从完整数据通路理解 NPU 的矩阵计算能力

NPU 的矩阵计算能力来自大量 MAC 或 tensor units、并行执行、专用 dataflow、scratchpad/VTCM、DMA、低精度计算和流水安排等共同作用。Ping-pong buffer 通过一块缓冲区计算、另一块缓冲区装载来重叠计算与数据搬运，是其中一种内存优化。

### 10. 分清 HeteroInfer Prefill 的 activation-centric partition

Prefill 的 sequence length 动态时，可以沿 activation 的 sequence 维切分。例如输入有 300 个 token、可用 NPU 图覆盖 256 个 token，就可以让 NPU 处理固定的 256 块，让 GPU 处理剩余 44 个 token。这种切分利用 NPU static graph 处理匹配部分，GPU 承担动态 remainder；若没有合适固定块，动态算子可由 GPU 单独执行。

### 11. 分清 HeteroInfer Decode 的 weight-centric partition

Decode 中许多 Linear 的新输入 shape 固定为 `[1, d]`，适合使用预先构建的 NPU graph。对这类计算，可以把权重划分给 GPU 和 NPU，让两边并行计算并合并结果，主要目标是提升整体内存带宽利用率。这与 Prefill 沿 activation 切 sequence、处理动态 remainder 是不同的优化；动态且无法映射到 NPU static graph 的算子仍可由 GPU 单独执行。
