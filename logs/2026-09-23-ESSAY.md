# Mobile LLM 论文整理（2026-09-23）

| 论文 | 研究对象 | 它发现的问题 | 核心解决方法 / 做法 | 最值得记住的 insight | 我们讨论时认为的脆弱处 / 可继续追问 |
|---|---|---|---|---|---|
| **When NPUs Are Not Always Faster** | llama.cpp + Qualcomm NPU 上的 mobile LLM | “NPU 一定比 CPU 快”不成立。Prefill 中某些 NPU `MUL_MAT` 甚至比 CPU 慢；Decode 单个 NPU kernel 虽快，但端到端收益很小。 | 从 end-to-end → Prefill/Decode → operator → communication / quantization / compute / scheduling 做层层 decomposition。 | **不能拿 accelerator peak TOPS 推断真实 LLM 性能。真正要看 phase、operator shape 和 software backend。** | 它测到的是特定 llama.cpp NPU implementation；“NPU 慢”不能直接解释成 Qualcomm NPU hardware 本身慢。 |
| **Is Your NPU Ready for LLMs?** | 多 framework × CPU/GPU/NPU 的 mobile LLM | 同一块 NPU 在不同 framework/backend 下性能可以差一个数量级；很多所谓“硬件比较”实际上被 software stack 强烈污染。 | 跨 llama.cpp、MNN、GENIE/QNN 等 framework/backend 做系统 characterization。 | **真正的比较单位不是 CPU vs GPU vs NPU，而是 `model × framework × backend × device`。** 一个差的 NPU backend 可以让 NPU 看起来远弱于 GPU。 | 关于 context length / static graph 导致 Decode degradation 的部分存在因果混杂：KV traffic、kernel shape、memory bandwidth 和 static provisioning 没有完全被拆开。 |
| **HeteroInfer, SOSP ’25** | 手机端 GPU + NPU 异构 LLM inference | Mobile NPU 喜欢 static/fixed shape，但 LLM 的 prompt length、context、部分 operator 都是动态的；单独 NPU 或 GPU 都不能很好利用 SoC。 | Prefill 将动态 token sequence 切成适合 NPU static graph 的部分和 GPU dynamic remainder；Decode 根据 operator/shape 做 GPU/NPU heterogeneous execution，并优化同步。 | **NPU 的限制不只是“算力”，而是 static-graph/shape constraint；GPU 的价值是补 NPU 的动态性。** 同时它把 mobile SoC 的 UMA、GPU/NPU bandwidth、shape sensitivity 摸得很清楚。 | heterogeneous partition 本身依赖 tensor shape、同步成本和 device profile；它对 foreground interference 的边角实验后来很可能成为 SERENO 继续往下挖的矿。 |
| **llm.npu, ASPLOS ’25** | 在 mobile NPU 上运行 LLM | NPU 依赖固定 static graph，而真实 prompt/sequence length 是动态的；每种长度重新生成 graph 代价太高。 | 用固定大小的 chunk / 预编译 graph 等方式，把动态 sequence 映射到 NPU 可接受的 static execution。 | **dynamic sequence × static accelerator 是 mobile LLM 的根本 mismatch 之一。** “静态图”不是不能跑 LLM，而是需要 padding/chunk/bucket 等 adaptation。 | 固定 chunk/bucket 会引入 padding waste、graph switching 和 utilization 问题；最佳 bucket/chunk 往往依赖模型和硬件。 |
| **NPUGen: NPU as KV Generator for Stable Long-Context Mobile LLM Inference, MobiCom ’26** | 长上下文 mobile LLM 的 KV cache 管理与恢复 | 长 context 下 KV cache 占用越来越大；传统压缩会带来精度/性能 trade-off，而 storage offloading / context restoration 又可能产生不可预测 stall。作者进一步利用了一个 mobile SoC 特性：CPU 和 NPU 可以并行工作，而 NPU 在部分阶段可能有空闲算力。 | 不把丢失或被移除的 KV 全部从 storage 读回来，而是让 **NPU 重新生成 KV**；前台推理与后台 KV regeneration 并行，并配合 scheduling / QoS control 来限制 regeneration 对 foreground inference 的影响。 | **“恢复 context”不一定只能靠 storage I/O；可以用 compute 换 memory / I/O。闲置 accelerator 本身可以成为一种 memory-management resource。** 这把 KV management 从“存还是删”扩展成了“存、恢复、重新计算”的三者权衡。 | 它的核心 setting 是 **CPU-side foreground inference + NPU background KV generation**，而且 regeneration 本身也会消耗 shared DRAM bandwidth；因此和之前考虑的 **NPU foreground inference + CPU/UFS restoration** 有部分重叠，但方向相反。它已经覆盖了“异构 context recovery 与 foreground inference 共存会产生资源竞争”这一类问题，所以以后不能只把“CPU/NPU overlap 会有 DDR contention”本身当 novelty。 |
