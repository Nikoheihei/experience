## 1. Speculative Decoding 的基本原理

Speculative Decoding 的核心是利用计算成本较低的 Draft Model 提前生成多个候选 Token，再交给 Target Model 通过一次 Forward Pass 并行验证。

- **Draft 和 Target model 生成方式：**1. 联合训练。2. 直接使用两个预训练模型。3. 通过蒸馏训练 Draft。KnapSpec 则采用 training-free 的方式，从 Target 中选择部分 Attention 和 MLP 模块构造 Draft。
- **Target 提供的补充 Token 会成为下一轮 Draft 的上下文。** 如果某个候选被拒绝，Target 需要提供修正 Token；如果全部接受，则可以额外生成一个 Token。

Sampling Decoding 需要 Residual Distribution。

Draft 和 Target model 的概率分布不一定相同。如果某个 Token 已经通过 Acceptance Mechanism 获得了部分概率质量，那么拒绝后直接按照 Target 原始分布重新采样，就可能重复分配概率质量，从而改变最终输出分布。

`p_residual(x) ∝ max(0, p(x) - q(x))`

本质上是把尚未分配的概率质量补齐。

**这个机制保证的是采样正确性，而不是直接提升推理性能。**

另外，论文的 Expected Tokens per Step：

`E[N] = 1 + α + α² + ... + α^γ`

来自截断几何分布。其中 α 是每个位置具有相同条件接受概率的简化假设。现实里不同位置的 Acceptance Rate 未必相同，因此这个公式更适合用于性能建模。

## 2. Self-Speculative Decoding 与普通 Speculative Decoding

传统 Speculative Decoding 通常需要一个额外的 Draft Model 来预测 Token，再由 Target Model 进行 Verification。这会带来额外的模型部署和维护成本，而且 Draft 与 Target 的概率分布差异可能降低 Acceptance Rate。

**Self-Speculative Decoding 则直接利用 Target Model 自身构造一个计算成本更低的 Draft。** 这样不需要维护完全独立的 Draft Model，也能共享部分模型参数，某些实现还可以复用中间计算结果。

目前常见的实现方式有两种：

### ① Early-exit（提前退出）

假设 Target 有 32 层 Transformer Blocks，Early-exit 只执行前 16 层，就提前通过 LM Head 预测下一个 Token。

Draft 阶段：

`Input → Layer 1 → ... → Layer 16 → LM Head`

Verification 阶段仍然使用完整的 32 层模型。

它的优点是实现思路简单，Draft 的计算量可以通过 Exit Depth 控制。

但缺点也很明显：

- 只能保留模型前面的连续层，无法灵活选择后面的重要层；
- 中间层的 Hidden States 未必适合直接进行 Token Prediction；
- Exit Layer 越浅，Draft 虽然越快，但 Acceptance Rate 可能越低。

代表工作有 LayerSkip 和 DEL。LayerSkip 还通过 Layer Dropout 和 Early-exit Loss 训练模型，提高中间层提前预测的准确性。

### ② Layer-skip（选择性跳层）

Layer-skip 不再要求 Draft 只能使用前面连续的层，而是允许跳过模型中任意位置的部分模块。

例如完整模型有 8 层：

`Target: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8`

Draft 可以选择：

`Draft: 1 → 2 → 4 → 6 → 8`

这样就有机会跳过不太重要的层，同时保留后面对于预测有帮助的层。

不过，这也引入了新的问题：**究竟应该跳过哪些层？**

假设一共有 `L` 个 Transformer Blocks，如果把每个 Attention 和 MLP 都视为独立的选择对象，那么理论上有 `2^(2L)` 种组合。

所以 Layer-skip 的核心问题就变成了如何高效地寻找合适的子网络。

代表工作包括 SWIFT、CLaSp 和 KnapSpec：

- SWIFT 使用 Bayesian Optimization 搜索 Layer Subsets；
- CLaSp 在固定层数预算下，通过 Cosine Similarity 和 DP 选择跳层方案；
- KnapSpec 进一步把 Attention 和 MLP 分开考虑，根据 Context Length 预测它们的 Latency，并使用 Knapsack DP 构造候选方案，最终优化 TPT。

## 3. Latency Modeling 和 Integer Weight Normalization

**对于固定的 Dense Transformer，在 Tensor Shape、Context Length 和硬件状态基本不变的情况下，即使输入的具体数值不同，Attention 和 MLP 的执行耗时通常也比较稳定。**

因为矩阵乘法的维度、运算量以及内存访问规模基本不变。

不过，Decode 阶段 Attention 需要访问 KV Cache，所以其耗时会随 Context Length 变化，而 MLP 的计算量基本不受 Context Length 影响。

KnapSpec 因此采用：

- `t_MLP = c1`
- `t_Attn(n) = c2 × n + c3`

这些系数通过 Offline Profiling 拟合得到。

在线推理时，系统不需要重新测量每一层的实际耗时，而是根据当前 Context Length 直接计算预测延迟。

接下来就是 Integer Weight Normalization。

我一开始把这里的 Weight 理解成了神经网络的权重矩阵，后来才反应过来，**这里的 Weight 指的是背包问题中的物品重量，实际上是执行延迟的离散化表示。**

作者定义：

`Δ = min(t_Attn(n), t_MLP)`

然后将两种模块的延迟除以 Δ 并取整，得到整数权重。

这样做不是为了优化模型计算本身，而是为了将连续的 Latency 转换为整数 DP 可以处理的成本。

不过这里存在两个近似：

1. 离线预测的延迟可能与实际运行时不同。
2. 整数化会引入额外的舍入误差。

尤其在 GPU Contention、动态 Batching 或硬件状态变化时，离线 Latency Model 未必仍然准确。

## 4. KnapSpec 的 DP 到底在做什么？

这是今天花时间最多、目前还没有完全掌握的部分。

首先，KnapSpec 的 DP 和传统 0/1 Knapsack 有一个很大的区别。

传统 Knapsack 的 DP State 通常保存一个标量收益，但 KnapSpec 定义：

`g[i, j] ∈ R^(r×d)`

表示处理完前 i 个模块，累计跳过权重为 j 时，算法保留下来的最佳 Hidden State。

**这里 j 不是层数，而是累计跳过的计算成本。**

对于当前模块，DP 考虑两个候选：

- **Execute：** `h_e = f^(i)(g[i-1,j])`
- **Skip：** `h_s = g[i-1,j-w_i]`

Execute 不会增加跳过的成本，因此从相同预算 j 的上一层状态转移。

Skip 则会增加当前模块的跳过权重，因此需要从 `j-w_i` 转移。

随后分别计算两个候选与完整 Target 在当前层的 Hidden State `X^(i)` 的 Cosine Similarity，保留相似度更高的候选。

这里还有一个容易误解的地方：

**Cosine Similarity 并不是直接比较执行当前层与跳过当前层的两个结果，而是分别比较这两个候选与完整 Target 的参考表示。**

j 的作用也逐渐理解了。它把不同计算成本的候选方案分开，让 DP 在相同 Skipped Weight 下选择较好的 Hidden State。

如果只优化 Cosine Similarity，不限制跳过成本，那么最好的方案当然是什么都不跳过，这样 Draft 就失去了加速意义。

## 5. Single-pass Efficiency

作者定义：

`K = L × (w_Attn + w_MLP)`

也就是所有可选模块的整数权重之和。

DP 只需要运行一次，就可以得到多个不同 Skipped Budget 下的候选配置，而不是针对每个 Budget 重新搜索。

此外，在固定的第 i 层，不同 j 的状态只依赖第 i-1 层已经计算好的结果，因此不同 Budget 的 Forward Pass 和 Cosine Similarity 可以通过 Batching 并行执行。

但这不等于搜索成本很低。

因为 KnapSpec 的 DP 保存的是 Hidden States，而不是几个标量。为了比较不同候选，系统还需要实际执行模块 Forward Pass。

作者通过并行计算（还没动）、Pruning，以及周期性更新 Draft Configuration 来减少这部分 Overhead。

今天也终于分清了：**优化间隔中的 64 Steps 是 64 次 Speculative Decoding Iterations，而不是 64 个输出 Token。**

## 6. 对这篇论文目前的看法

我现在有点怀疑这篇论文的方法是不是过于复杂了。

尤其有三个问题：

**第一，DP 是否真的具有合理的最优子结构？**

当前层 Cosine Similarity 更高的 Hidden State，经过后续 Transformer Layers 后，不一定仍然更接近 Target。

但作者在每个 DP State 中只保留一个候选，可能提前丢弃最终表现更好的方案。因此这个方法更像启发式的近似搜索，而不是具有经典 Knapsack 最优性保证的 DP。

**第二，复杂的搜索是否真的有必要？**

DP 需要额外执行大量 Forward Pass，即使能够 Parallelize，也需要占用 GPU 资源。

我更想知道，相比一个简单的 Context-length-aware Heuristic，复杂 DP 到底贡献了多少额外加速。

**第三，Latency Model 在真实 Serving 环境里是否足够准确？**

目前的建模比较依赖稳定的硬件运行状态。如果存在动态 Batching 或 GPU Contention，是否仍能选择正确的 Draft Configuration？

不过，这些目前只是我的疑问，不能仅凭这些就断定论文不好。后面还需要结合实验与消融分析。

## 总结与 Profiling

### 一、Proxy Metrics：如何选择一个合理的优化指标？

今天讨论 KnapSpec 时，我意识到一个问题：

**很多 Systems Optimization 的最终目标都是改善真实性能，但直接测量或者优化 End-to-end Performance 往往比较昂贵，所以研究者会选择一个更容易计算的 Proxy Metric（代理指标）。**

例如在 Speculative Decoding 中，真正关心的是实际吞吐量（Throughput）或 Token 生成延迟。

但搜索 Draft Subnetwork 时，如果每测试一个配置，都完整运行推理并测量吞吐量，搜索成本可能很高。

因此，可以建立一条关系：

`Cosine Similarity → Acceptance Rate → Expected Accepted Length → Throughput`

但这条关系并不是严格等价的。

#### 1. 如何选择 Proxy Metric？

我觉得至少要考虑两个方面。

**第一，Proxy Metric 是否和最终性能有明确的机制联系？**

不能因为两个指标看上去相关，就直接拿一个代替另一个。

例如：

- Cosine Similarity 衡量 Hidden States 的方向相似性；
- Acceptance Rate 衡量 Draft Token 被 Target 接受的可能性；
- Throughput 同时受到 Acceptance Rate、Draft Latency、Verification Latency 和搜索开销的影响。

因此，即使 Cosine Similarity 和 Acceptance Rate 存在正相关，也不能直接说明 Cosine Similarity 越高，Throughput 就越高。

**第二，这个 Metric 是否足够便宜？**

假设某个指标能非常准确地预测 Throughput，但计算它所需要的时间接近一次完整推理，那么它作为 Online Optimization 的 Proxy 就没有太大意义。

因此需要同时考虑：

- **Predictive Accuracy**：能否预测真实性能？
- **Evaluation Cost**：获取这个指标需要多少时间和计算资源？
- **Generalizability**：换模型、上下文或者硬件以后还是否有效？

一个相对不那么准确、但计算成本极低的 Metric，有时反而更适合在线系统。

#### 2. 如何证明 Proxy Metric 与真实性能相关？

##### ① Pearson Correlation Coefficient（PCC）

PCC 用于衡量两个变量之间的线性相关程度：

`r = Cov(X, Y) / (σ_X × σ_Y)`

取值范围为 `[-1, 1]`。

- `r` 接近 1：较强的正线性相关；
- `r` 接近 -1：较强的负线性相关；
- `r` 接近 0：没有明显的线性相关，但仍可能存在非线性关系。

例如，测量不同 Draft Configurations 的 Cosine Similarity 和 Acceptance Rate，计算 PCC。如果 `r = 0.92`，可以说明在这些样本中，两者存在较强的正线性相关。但 **PCC 高并不代表因果关系，也不保证对每个配置都能正确排序。**

另外，如果不同配置的 Context Length 差异很大，那么观测到的相关性可能部分来自 Context Length，而不完全是 Proxy 本身的预测能力。因此，需要在相同 Context Length、Draft Length 等条件下进行分组分析。

##### ② Coefficient of Determination（R²）

R² 通常用于衡量回归模型对真实数据变化的解释程度：

`R² = 1 - SSE / SST`

其中：

- `SSE`：模型预测误差的平方和；
- `SST`：真实数据相对于均值的总平方和。

##### ③ Spearman Rank Correlation

这个指标对 Systems Optimization 可能特别重要。

因为很多时候并不关心 Proxy 能否准确预测具体的 Throughput 数值，而是关心：

**它能不能正确判断方案 A 比方案 B 更好？**

Spearman 主要衡量两个变量之间的单调关系，通过比较变量的排名进行计算。

例如：

| Config | Proxy 排名 | 真实 Throughput 排名 |
|---|---:|---:|
| A | 1 | 1 |
| B | 2 | 3 |
| C | 3 | 2 |
| D | 4 | 4 |

即使 Proxy 不能准确预测 Throughput 的数值，只要排名基本一致，它就可能适合作为配置搜索的目标。

相比之下，PCC 更关注数值之间的线性关系。此外，还可以使用 Kendall's Tau 衡量成对排序的一致性。

##### ④ Decision Quality：直接验证优化决策

既然使用 Proxy 的最终目的是选择更好的配置，那么就应该直接比较它选出来的配置和真实最优配置。

假设：

- 通过实测找到候选集合中吞吐量最高的配置 `S*`；
- 使用 Proxy 找到配置 `S_p`。

可以计算：

`Regret = T(S*) - T(S_p)`

也可以使用归一化指标：

`Normalized Regret = [T(S*) - T(S_p)] / T(S*)`

这里 `T` 表示实际吞吐量。

Regret 越小，说明 Proxy 选出来的配置越接近真实最优配置。

这比只报告 `PCC = 0.95` 更有说服力。因为可能存在一种情况：某个 Proxy 整体相关性很高，但总是在最优配置附近发生排序错误，最后导致实际性能损失。从优化决策的角度看，这种 Proxy 仍然可能不够好。
